## 4. 第二轮：隔离 AMD I2C（AMDI0010）控制器驱动

### 4.1 为什么怀疑它（Phase 2 分析结论）

**① 触摸板确实挂在 AMDI0010 上。** DSDT 反编译（`iasl -d`）结果：

| DSDT 设备 | `_HID` | `_UID` | `_CRS` |
|---|---|---|---|
| `\_SB.I2CA` | `AMDI0010` | 0 | IRQ 10，MMIO `0xFEDC2000` |
| `\_SB.I2CB` | `AMDI0010` | 1 | IRQ 11，MMIO `0xFEDC3000` |
| `\_SB.I2CC` | `AMDI0010` | 2 | IRQ 4，MMIO `0xFEDC4000` |
| `\_SB.I2CD` | `AMDI0010` | 3 | IRQ 6，MMIO `0xFEDC5000` |

触摸板是 `\_SB.I2CA.TPD0`：`_CID = PNP0C50`，`_CRS` 用 `I2cSerialBusV2(0x0015, "\\_SB.I2CA")`
+ `GpioInt("\\_SB.GPIO", pin 8)`；`_HID` 返回 `ASUF1208`/`ASUP1208`/`MSFT0001`。
另有 `\_SB.SMKB`（`ITE5570`，也是 `PNP0C50`）挂在 `\_SB.I2CD`。
→ **所以 VoodooI2C 去 attach AMDI0010 不是"无关的旁支"，它正是触摸板所在的控制器。**

**② 该控制器匹配的是 ACPI 个性，不是 PCI。** 从卡上 `VoodooI2C.kext/Contents/Info.plist` 读出：

* `VoodooI2CACPIAmdWtController`：`IOClass = VoodooI2CACPIController`，`IONameMatch = AMDI0010, AMDI0510`，`IOProbeScore 9999`
* `VoodooI2CPCIController` 的 4 个个性**全部**是 Intel `IOPCIMatch`（`0x9de88086`、`0x06e88086`、`0x34e88086`、`0x9d608086`/`0xa1608086`）

> ⚠️ **需要你核对原始照片**：你给的最后一行是 `VoodooI2CPCIController::AMDI0010`。
> 但按上面这两条，能匹配 AMDI0010 的**只能是 `VoodooI2CACPIController`**
> （`VoodooI2CController.cpp` 第 138 行的格式是 `"%s::%s Starting I2C controller" = 服务名::provider 名`；
> 只有 ACPI 个性会以 `AMDI0010` 作为 provider）。
> **很可能是把 `VoodooI2CACPIController` 读成了 `VoodooI2CPCIController`** ——
> 和之前把 `IOAPIC: Version 0x21` 误读成 `Assertion failed` 是同一类错误。
> 这不改变结论（两种情况下都停在控制器 `start()`），但请据原图确认。

**③ `Starting I2C controller` 之后本应紧接着打印什么。**
`VoodooI2CACPIController::start()`（v2.9.1 源码）：

```
50  bool VoodooI2CACPIController::start(IOService* provider) {
51      if (!super::start(provider)) return false;      // ← 内部第 138 行打印 "Starting I2C controller"
55      physical_device.acpi_device = OSDynamicCast(IOACPIPlatformDevice, provider);
57      …AccessIntrMaskWorkaround 属性（我们没设，无输出）
63      setACPIPowerState(kVoodooI2CStateOn);           // ← 应打印 "Set ACPI power state _PS0"
65      if (mapMemory() != kIOReturnSuccess) { "Could not map memory"; return false; }
70      if (publishNub() != kIOReturnSuccess) { "Could not publish nub"; return false; }  // ← 内部打印 "Publishing nub"
75      registerService();
```

而 `VoodooI2CController::start()` 第 138–148 行在打印之后还会做
`provider->retain()` → `provider->open(this)` → `setProperty(…)`。

→ **若 `Starting I2C controller` 确实是最后一行，那么卡点在它之后的极窄区间**
（`provider->open()` 或紧随的 `setACPIPowerState`/`mapMemory`），
**下一行预期是 `Set ACPI power state _PS0`**。
这只是**假设**：最后一行不等于死锁点，且屏幕会滚。

**④ `-vi2c-force-polling` 不作用于控制器。** 它只在
`VoodooI2CDeviceNub.cpp` 第 236–242 行被读取：

```cpp
bool force_polling = checkKernelArg("-vi2c-force-polling");
…
if (force_polling) { IOLog("…Forced polling mode, skipping GPIO interrupts\n"); return kIOReturnSuccess; }
```

而 `VoodooI2CDeviceNub` 是**控制器启动成功之后**才由
`VoodooI2CControllerDriver::publishNubs()` 创建的。所以：

* 它能省掉 `getGPIOController()` 里那个 **1 秒** 的 `waitForMatchingService`（第 267 行），
  以及 GPIO 引脚相关的取资源路径；
* 但它**完全无法**阻止 AMDI0010 控制器本身的 attach 卡住；
* 而且**本轮没有任何证据证明它生效了** —— 因为还没走到 device nub 那一步。
  （生效时应看到 `Forced polling mode, skipping GPIO interrupts`。）

**⑤ AMD 专用代码只在总线配置里。** `VoodooI2CControllerDriver.cpp` 第 68–76 行
`getClkRateFor()` 对 `AMD0010` 返回 133 MHz、对 `AMDI0010`/`AMDI0019` 返回 150 MHz，
用于算 SDA hold 时间；调用点在 `getBusConfig()`，**在控制器 start 之后**。
即：AMDI0010 有专门的时钟表，但**控制器 attach 阶段没有任何 AMDI0010 专用分支**。

### 4.2 依赖关系（读卡上每个 kext 的 `OSBundleLibraries`）

```
com.alexandred.VoodooI2C       requires  com.alexandred.VoodooI2CServices >= 1.0
                               requires  org.coolstar.VoodooGPIO       >= 1.1
com.alexandred.VoodooI2CHID    requires  com.alexandred.VoodooI2C       >= 2.0
me.kishorprins.VoodooInput     requires  仅 IOHIDFamily + kpi.*
as.acidanthera…PS2Controller   requires  仅 IOACPIFamily + kpi.*
as.acidanthera…PS2Trackpad     requires  PS2Controller + IOHIDFamily + kpi.*   ← 不含 VoodooInput
```

* `{VoodooI2C, VoodooGPIO, VoodooI2CServices}` 是**闭集**：只禁用控制器会留下一个装不全的家族。
* `VoodooI2CHID` 硬依赖 `VoodooI2C` → 必须一起禁。
* 卡上存在**两份** `VoodooInput`（`VoodooI2C.kext/Contents/PlugIns/` 与
  `VoodooPS2Controller.kext/Contents/PlugIns/`），bundle id **完全相同**：
  `me.kishorprins.VoodooInput` v1.1.7 → **只能启用一份**（当前正是如此：I2C 那份启用、PS2 那份禁用）。

关于"能否在禁用 I2C 时保留 VoodooInput"：

* `VoodooInput` 的 `OSBundleLibraries` 只有 `IOHIDFamily` + `kpi.*`，**独立可加载**；
* OpenCore 的 `Kernel.Add` 是**按 `BundlePath` 逐条注入**，没有"父 bundle/插件"概念，
  所以**禁用父条目 `VoodooI2C.kext` 之后，嵌套的 `VoodooInput.kext` 条目仍会被正常注入**；
* 二进制扫描：`VoodooPS2Trackpad` 的可执行文件里含 `VoodooInput` / `VoodooInputSupported` 字符串
  —— 这是**运行时按字符串查找**的软依赖（未写进 `OSBundleLibraries`），
  而它自己也会 advertise `VoodooInputSupported`，所以保留一份 VoodooInput 即可满足它。
* ⇒ **方案 A（本轮采用）：4 项设为 `false`，VoodooInput 原样保持启用。** 只动 4 个布尔值。

> 方案 B（备选，仅当 A 出现依赖问题）：把它改为启用 `VoodooPS2Controller.kext/…/VoodooInput.kext`、
> 禁用 `VoodooI2C.kext/…/VoodooInput.kext`，让 VoodooInput 彻底不依赖 I2C bundle。
> 代价是变成 5 处改动，**不如 A 干净**，所以作为后备而非首选。
>
> 方案 C（更彻底的触控板隔离，仅当 A 出问题）：再禁用 `VoodooPS2Trackpad`，只留
> `VoodooPS2Controller` + `VoodooPS2Keyboard` + `VoodooPS2Mouse`，用 USB 鼠标。
> 由 §4.1④ 已知 I2C 与 force-polling 的关系，C 的额外信息量有限，故不作为本轮。

   其余字节原样保留（diff 只显示真实改动）

   序列号 / MLB / UUID（**含字节序反转形式**）/ MAC（冒号、连字符、紧凑三种写法）/

   另外拒绝未脱敏的 `NVMe(0x1,…)`、`Report.json`、`*.aml`、`*.bin`、`>1MB` 文件

### 6.1 已发生的泄漏与修复（D7，务必留档）

`v1.0`（`e8c329b`）发布的 4 份日志中，`OC: Setting system-id <UUID-REDACTED>` 那一行
**保留了真实 SMBIOS UUID**（本文件不重复该值，以免二次泄漏）。原因有两个，都已修掉：

* 当时的校验只搜了配置里 UUID 的**原字符串写法**，而 OpenCore 打印的是
  **前三个字段字节序反转**的形式 → 搜不到；
* 当时的核对命令把 `Get-ChildItem | Select-String -Quiet` 的结果当成了"哪个文件命中"，
  实际它把整条管道聚合成一个布尔值 → 误判为"已脱敏"。

修复：`scripts/scrub-log.py`（新增）+ `sync-to-github.ps1` 增加字节序反转 UUID、GUID 尾段、
未脱敏 `NVMe` 路径三类检查。**注意：修复只作用于当前分支内容，旧提交里仍可追溯。**
