## 1. 已确认异常（有日志或源码直接支撑）

| ID | 异常 | 证据 | 影响 |
|---|---|---|---|
| **D1** | `boot-args` 自第 1 次引导起被冻结；`npci=0x2000` **从未生效** | `OCVAR: …:boot-args - ignored, exists`；`MBA:OUT` 无 npci；`OpenCoreNvram.c` 的 `OcAddNvram(…, FALSE)` + `Delete` 未列 `boot-args` | 23:30 之后加入的所有 boot-arg 都是惰性的 |
| **D2** | 卡上存在**从未引导**的第二档（`DevirtualiseMmio=False`） | 最新日志 `DEVMMIO 1` vs 配置 `False` | 会把"未测试"误读成"已失败" |

| **D4** | 文档里"加 npci 实测越过了"的归因**站不住** | 而 npci 在任何有日志的引导中都没进内核 | 归因需改写，否则掩盖真正变量 |
| **D5** | 仓库配置曾 ≠ 最后实测配置 | 仓库那份当时 = round0 | 读者会以为第二档已验证 |
| **D6** | `SSDT-Disable_Network_GPP6` 是**无效注入**，并白送 1 次 ACPI 表加载失败 | `ACPI Error: [\_SB.PCI0.GPP6.WLAN._DSM] … AE_ALREADY_EXISTS` —— 固件自带 `WLAN` SSDT 已定义该 `_DSM` | 3 个失败之一 |

### 不得当作故障的现象

### 可疑但未证实

## 3. 第一轮：让 `boot-args` 真正生效

**唯一实验变量**：把 `boot-args` 加入 `NVRAM → Delete`，使 OpenCore 的删除阶段清掉那份冻结的
旧值，从而让 `NVRAM → Add` 里**已经写了很久但从未生效**的 `npci=0x2000` 第一次真正进入内核。

### 3.3 明确**不动**的东西

### 3.4 校验

```
ocvalidate 1.0.9 (DBG)  ->  No issues found   exit=0
```
校验器取自 `OpenCore-1.0.9-DEBUG.zip`，与该 U 盘上的 OpenCore（`OC: OpenCore DBG-109-2026-10-10`）
同版本。

### 3.5 判定标准

**成功**（引导后 1 秒内即可判定，不需要等到图形界面）：

```
OC: Deleting NVRAM 7C436110-AB2A-4BBB-A880-FE41995C9F82:boot-args - Success
OCVAR: Setting NVRAM 7C436110-AB2A-4BBB-A880-FE41995C9F82:boot-args - Success
```
且 `AAPL: #[EB|MBA:OUT]` 中出现 `npci=0x2000`，且不再出现 `boot-args - ignored, exists`。

**失败 → 立即停止后续实验、继续追 NVRAM**：仍为 `ignored, exists`；或
`Deleting NVRAM …:boot-args` 状态非 Success；或 `MBA:OUT` 仍无 `npci=0x2000`。

**内核侧同时记录**：是否越过 `RTC: Only single RAM bank (128 bytes)`；是否出现新的 panic、
`AppleKeyStore`、`still waiting for root device`、或安装器界面；`OC: Prelinked status` 是否
仍为 `Success`。

> 从**第二轮引导起**，`boot-args` 会显示
> `OC: Not deleting NVRAM …:boot-args, matches add` + `ignored, exists` ——
> 那时这两个字样**恰恰证明值已经正确**（Flash 保护机制）。判定只以第一轮那次为准。

## 4. 第二轮候选（**先不要动**，等第一轮结果）

按优先级，且每轮只允许一个变量/一组不可拆分的关联参数：

1. **MAT 匹配的内存映射组合**（单组，不可拆分）：
   `EnableWriteUnprotector=False, RebuildAppleMemoryMap=True, SyncRuntimePermissions=True`
   依据：`OCABC: MAT support is 1` + Dortania `AMD/zen.md` 给反向组合的唯一前提是
   *"missing the `MEMORY_ATTRIBUTE_TABLE`"*。注意第 2、3 次引导**已经跑过**这组，但那两次
   `npci` 都没生效 —— 所以这是"在干净条件下重测"，不是"新解法"。
2. **最小 kext 诊断配置**：先排除与进入 Recovery 无关的外设驱动 ——
   WhateverGreen、VoodooI2C 及插件（Services/GPIO/Input/I2CHID）、Sinetek-rtsx、
   NullEthernet、HoRNDIS、SMCLightSensor、BrightnessKeys。**一次只动这一类。**
3. **删除 `SSDT-Disable_Network_GPP6`**（已证无效注入）→ 观察 ACPI 失败数 3→2。
4. **最后**才评估 SMBIOS 与图形初始化兼容性。

## 5. 同步约定（"每次修改后同步到 GitHub"的执行方式）

仓库必须**始终**反映卡上真实状态，否则又会重演 D5。固定流程：

1. 改完卡（或改完文档）后，用脱敏脚本把卡上配置搬到仓库：
   ```powershell
   python scripts\sanitize-config.py D:\EFI\OC\config.plist efi\config.plist
   ```
   该脚本只改 4 个身份字段（`SystemSerialNumber` / `MLB` / `SystemUUID` / `ROM`），
   **其余字节原样保留**，所以 diff 里只会出现真正的改动；任一字段找不到就直接失败退出，
   不会静默发布带真实序列号的配置。
2. 更新本文件的"结果"表与阶段状态；如需新增日志，把 U 盘根目录的 `opencore-*.txt` 复制到 `logs/`
   （日志本身不含身份信息，但**发布前仍要扫一遍** MAC/序列号）。
3. 跑 `scripts\sync-to-github.ps1`：它做脱敏 → `ocvalidate` → 泄漏扫描 → `git add/commit/push`
   → **最后把远端实际内容拉回来复核**（确认远端没有真实序列号）。
4. 提交信息写清"改了什么 + 依据哪条日志/源码"。

**绝不提交**：原始 `Report.json`（含网卡 MAC、磁盘序列号）、ACPI 转储（`MSDM` 表含 Windows
OEM 密钥）、构建产物、任何第三方二进制。
