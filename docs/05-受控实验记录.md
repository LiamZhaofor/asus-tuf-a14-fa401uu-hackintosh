### 1.3 一个**已确认的硬约束**：macOS 处理不了 8 GiB 的 BAR

OpenCore 官方文档（`Configuration.tex` 第 1848–1853 行）：

> *"This quirk reduces GPU PCI BAR sizes for Apple macOS up to the specified value or lower if it is unsupported. … While **Apple macOS supports a theoretical 1 GB maximum**, in practice all non-default values may not work correctly. For this reason **the only supported value for this quirk is the minimal supported BAR size, i.e. `0`**. Use `-1` to disable this quirk."*

⇒ 本机 8 GiB 的 BAR1 **超出 macOS IOPCIFamily 的处理上限**，`ResizeAppleGpuBars=0` 是**必需**的，
不是可选项。**本轮及下一轮都不动它。**

### 4.3 屏幕现象与**不能**下的结论

屏幕最后两行：

```
PCI configuration begin
IOPCIConfigurator::configure() PCI configuration PCI0
```

上方可见 `[addMemoryRange()] AppleVTD is not yet installed as gSystem`、AppleKeyStore、
AppleLockdownMode、AppleSSE。**无 panic / backtrace。**

## 5. `npci` / PCI / Above 4G：源码级分析（本轮新增，全部有出处）

### 5.1 `npci=0x2000` 到底做什么 —— Apple 源码

`IOPCIBridge.cpp`（`apple-oss-distributions/IOPCIFamily`）：

```c
if (PE_parse_boot_argn("pci",  &debug, sizeof(debug)))
    gIOPCIFlags |=  debug;          // pci=  -> 置位
if (PE_parse_boot_argn("npci", &debug, sizeof(debug)))
    gIOPCIFlags &= ~debug;          // npci= -> 清位（是 pci= 的取反）
```

默认值（同文件）：

```c
uint32_t gIOPCIFlags = 0
    | 0*kIOPCIConfiguratorFPBEnable
    | kIOPCIConfiguratorPFM64            // <-- 默认已置位
    | kIOPCIConfiguratorCheckTunnel
    | kIOPCIConfiguratorTBMSIEnable
    ...
```

位定义（`IOKit/pci/IOPCIConfigurator.h`）：

```c
kIOPCIConfiguratorNoTB         = 0x00000800,
kIOPCIConfiguratorTBMSIEnable  = 0x00001000,
kIOPCIConfiguratorPFM64        = 0x00002000,     // <<<< 就是这一位
kIOPCIConfiguratorBoot         = 0x00004000,
```

⇒ **`npci=0x2000` = 清除 `kIOPCIConfiguratorPFM64`。**

PFM64 的作用（`IOPCIConfigurator.cpp`）：

```c
#define PFM64_SIZE     (2ULL*GB)      // 默认窗口 2 GB
#define PFM64_MIN_SIZE (512*MB)
#define PFM64_MAX_SIZE (16ULL*GB)
#define PFM64_MAX      (1ULL<<44)     // 上限 16 TiB

// createRoot()：host bridge 有内存但没有 64 位窗口时，补一个合成窗口
if (hasHostMemory && !hasHost64 && !fAddedHost64) {
    cpuPhysBits = cpuid_info()->cpuid_address_bits_physical;
    size  = fPFM64Size;
    start = (1ULL << cpuPhysBits);
    if (start > PFM64_MAX) start = PFM64_MAX;
    start -= size;
    IOPCIRangeListAddRange(&bridge->ranges[kIOPCIRangeBridgeMemory], ..., start, size);
}

// 64 位 BAR / prefetchable 区间的地址上限
if (clean64) {
    range->flags |= kIOPCIRangeFlagBar64;
    if (kIOPCIConfiguratorPFM64 & fFlags) range->maxAddress = 0xFFFFFFFFFFFFFFFFULL;
}
if (bridge->clean64 && (kIOPCIConfiguratorPFM64 & fFlags))
    maxAddress[kIOPCIResourceTypePrefetchMemory] = 0xFFFFFFFFFFFFFFFFULL;
```

**⚠️ 勘误（本轮修正）**：我先前写的是"清除 PFM64 = 不再补合成窗口 + 收回 64 位上限"，
**这是过度推断**。逐处核对 `apple-oss-distributions/IOPCIFamily` 后，
`kIOPCIConfiguratorPFM64` 在源码里**只出现 5 次**：

| 位置 | 内容 | 是否**读**该标志 |
|---|---|---|
| `IOPCIBridge.cpp:181` | 默认 flags 初始化（**默认置位**） | 写入 |
| `IOPCIConfigurator.cpp:638` | `fFlags &= ~kIOPCIConfiguratorPFM64;`（Intel root / `CPUID_FEATURE_VMM` 时 Apple 自己关掉） | 写入 |
| `IOPCIConfigurator.cpp:2791` | `if (kIOPCIConfiguratorPFM64 & fFlags) range->maxAddress = 0xFFFFFFFFFFFFFFFFULL;` | ✅ 测试 |
| `IOPCIConfigurator.cpp:2923` | `if (bridge->clean64 && (kIOPCIConfiguratorPFM64 & fFlags)) maxAddress[kIOPCIResourceTypePrefetchMemory] = …ULL;` | ✅ 测试 |
| `IOPCIConfigurator.cpp:3546` | 同上（另一条 allocator 路径） | ✅ 测试 |

而**合成窗口那段（约 `IOPCIConfigurator.cpp:690`）并不检查该标志**：

```c
if (hasHostMemory && !hasHost64 && !fAddedHost64)   // 只有这三个条件，没有 PFM64
{
    size  = fPFM64Size;                             // ← 尺寸来自这里
    ...
}
```

`fPFM64Size` 默认 = `PFM64_SIZE`（2 GB，第 64 行），可由 `pci64=<MB>` 覆盖（第 149/157 行）。
两者共用 `PFM64_*` 这套宏名，容易误读成同一件事。

⇒ **准确表述**：`npci=0x2000` 清除 PFM64 标志，其**可确认的行为影响只有一处**——
取消"64 位 BAR（`clean64`）与 prefetchable 区间可落于 64 位地址空间任意位置"这一许可
（把 `maxAddress` 从全 1 改回默认上限）。
它**不等于"完全关闭 64 位 MMIO"**：合成窗口照旧创建，尺寸另由 `fPFM64Size` 决定。

> 附注：当 root 是某些 Intel 芯片组、或 **`CPUID_FEATURE_VMM`（跑在虚拟机里）** 时，
> IOPCIFamily 会**自己**清掉 PFM64（第 638 行）。即"PFM64 关闭"本身是 Apple 也会主动选择的合法状态。

### 5.2 这对本机意味着什么（**推论，非实测**）

结合 5.1 **已核实**的事实：PFM64 唯一可确认的作用就是那 3 处 `maxAddress` 许可。
本机 **Above 4G Decoding 已启用、BAR1 = 8 GiB 且位于 504 GiB** —— 这类设备的 64 位 BAR
正是靠"可落在 64 位地址空间任意位置"这条许可来安置。

* 因此**待检验的推论**是：清除 PFM64 收回了本机需要用到的 64 位安置余量；
* 但必须同时说明：**这只是推论**。也无法排除在 `clean64` 为假、或该许可实际未被用到的情况下，
  清除 PFM64 完全无影响。
* 另外，合成窗口那 2 GB（位于 ~16 TiB）与 GPU 的 504 GiB **不冲突**，所以"窗口"分支
  **不是**本机的问题来源。

⇒ 第三轮的价值**不是**"已知它会变好"，而是**第一次把 npci 变成一个被真正检验过的变量**。

### 5.3 `npci` 在本机是否有明确必要？—— **没有**
