# 引导排错实录 —— 每次都卡死的证据、根因与解法

> 这份记录的价值在于：**每个结论都有日志行或源码位置作依据**，而不是"试出来的"。
> 机型：ASUS TUF A14 FA401UU（Ryzen 7 8845H + RTX 4050 Laptop）。目标系统：macOS 15 Sequoia。

---

## 0. 我们的诊断工具箱

| 工具 | 作用 |
|---|---|
| `boot-args` 带 `-v debug=0x100 keepsyms=1` | 让内核把启动过程打在屏幕上 |
| `Misc → Debug → Target = 67`（0x43） | 让 OpenCore **把日志写到 U 盘根目录** `opencore-*.txt` |
| `Misc → Debug → AppleDebug = True` / `ApplePanic = True` | 把 boot.efi 的调试输出并入 OpenCore 日志；内核 panic 存到 U 盘 |
| 手机拍屏幕 + 裁切放大 | 屏幕上的内核日志没有落盘，只能拍。低分辨率照片用 Pillow 裁切+3~4 倍放大就能读清（脚本见 `scripts/read-screen-photo.py`） |
| 1401 的 `p1401.bootfix` | 直接读 U 盘日志做诊断（`findings()` / `apply()`） |

两条经验：

- **OpenCore 的日志一定会以 `AAPL: #[EB|LOG:EXITBS:START]` 结尾** —— 无论引导成功还是失败，
  因为交接之后 OpenCore 就不再写日志了。**所以"日志停在 EXITBS"本身不能证明卡在那里。**
- **日志文件是预分配 256 KiB 的**，正文之后是零填充。判断是否被"写满截断"要看
  **第一个零字节的偏移**，而不是文件大小。

### 四次引导的运行真值（后续所有推断的基准）

**配置文件和"实际上跑了什么"是两件事。** OpenCore 在 `OCABC:` 行里把该次引导**真正生效**的
quirks 打了出来，所以判断依据应该取这里，而不是取 `config.plist`：

```
OCABC: ALRBL 1 RTDFRG 1 DEVMMIO 1 NOSU 0 NOVRWR 1 NOSB 0 FBSIG 0 NOHBMAP 0 SMSLIDE 1 WRUNPROT 1 CLRTS 0
OCABC: FEXITBS 0 PRMRG 0 CSLIDE 1 MSLIDE 0 PRSRV 0 RBMAP 0 VMAP 1 APPLOS 0 RTPERMS 0 ARBAR 0 RBIO 0
                 ^^^^^^^^ DevirtualiseMmio      ^^^^^^^^^ RebuildAppleMemoryMap   ^^^^^^^^^ SyncRuntimePermissions
                                                     VMAP = SetupVirtualMap      WRUNPROT = EnableWriteUnprotector
```

| # | 日志 | boot.efi 时间戳 | DEVMMIO | WRUNPROT | VMAP | RBMAP | RTPERMS | `boot-args` 写入结果 | `MBA:OUT` 含 `npci` | 终点 |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `...-233441.txt` | — | 1 | 0 | 1 | 1 | 1 | **Success** | 不适用（当时还没加） | **DMG chunklist 校验中**（未到 boot.efi） |
| 2 | `...-235506.txt` | 23:55:51 | 1 | 0 | 1 | 1 | 1 | `ignored, exists` | **否** | `EXITBS:START` |
| 3 | `...-001004.txt` | 00:10:46 | 1 | 0 | 1 | 1 | 1 | `ignored, exists` | **否** | `EXITBS:START` |
| 4 | `...-002330.txt` | 00:24:13 | 1 | **1** | 1 | **0** | **0** | `ignored, exists` | **否** | `EXITBS:START` |

三条从这张表直接读出来的结论：

1. **`npci=0x2000` 一次都没有生效。** 只有第 1 次真正写入了 `boot-args`，而那次的配置里还没有 `npci`。
2. 第 2、3 次跑的是 Dortania 的 **MAT 组合**；第 4 次才是"无 MAT"组合。**两个组合都没过关。**
3. 第 4 次之后（00:35）写入的 `DevirtualiseMmio=False` **从未引导过** —— 属于"准备测试"，不是"已失败"。

> 判定的起点永远是 `OCABC:` 行 + `OCVAR:` 行 + `AAPL: #[EB|MBA:OUT]` 行，
> 而不是 `config.plist` 的字面值。

## 1. OpenCore 菜单出现，但停在 `Timeout`，按键无反应

### 现象
OpenCore 菜单正常渲染（`1401 (external) (dmg)` / `Windows` / `Reset NVRAM`），
页脚显示 `Choose the Operating System: Timeout`，按任何键无反应，且似乎不会继续。

### 第一直觉（错的）
"笔记本内置键盘在 OpenCore 里不工作"。查配置发现 `KeySupport = True`、`KeySupportMode = Auto` 本就正确
（OpenCore 文档：`Auto` 按 `AMI → V2 → V1` 优先级自动选择，本机是 AMI Aptio 固件）。

### 日志给出的真相
```
04:923 OCB: Showing menu...
09:988 05:020 OCHK: FreeHotKeys                      ← 5 秒倒计时正常走完
10:021 00:010 OCB: Should boot from 1. 1401 (...)     ← 自动选中了安装器
10:051 00:019 OCRAM: Extent allocation of 888615275 bytes (A) gave 100000000
37:505 27:453 OCRAM: SHA-256 Digest is: C9FFF24B...   ← 27.45 秒算了 847 MiB 的 SHA-256
37:517 00:011 OCB: Found chunklist BaseSystem.chunklist for DMG BaseSystem.dmg[10]
（日志到此为止）
```

**键盘从来没问题，选择器自己走完倒计时并开始引导了。** 那句 `Timeout` 是倒计时*结束*的标识。

### 根因
`Misc → Security → DmgLoading = Signed` 会走这段（`DmgBootSupport.c` 第 131 行起）：

```c
if (DmgLoading == OcDmgLoadingAppleSigned) {
    OcAppleChunklistVerifySignature(...);   // RSA 验签
    OcAppleDiskImageVerifyData(...);        // 85 个分块 / 847 MiB 的 SHA-256
}
```

**这一段按设计没有任何日志输出** —— 该文件里所有*失败*分支才打日志
（`DMG is not trusted`、`DMG has been altered`、`Failed to install DMG Block I/O`、
`Failed to get bootable file off DMG`），成功路径是静默的。

此外 U 盘读取速度实测只有 **38.9 MB/s（USB 2.0 水平）**，所以这段特别久。

### 验伪/验证
- **日志没有被截断**：正文只占 262144 字节中的 **42521 字节（16.2%）**，且最后一行有完整 `\r\n`。
  → 说明 OpenCore 确实停在那里没再写，不是"写满丢掉了后面的内容"。
- 后来又启动了一次（`DmgLoading` 仍为 `Signed`）就过去了 → **证实这段只是慢，不是卡死。**
  （这一点我们一开始判断错了，特此记录：别把"静默的长阶段"当成死机。）

### 解法
1. **等**（1–2 分钟）；或
2. `Misc → Security → DmgLoading = Any` → 整段跳过。
   合法性：只有当 `SecureBootModel != Disabled` 时才会报
   `Cannot use Secure Boot with Any DmgLoading`；本机 `SecureBootModel = Disabled` ✅

## 2. `PCI configuration begin`

### 现象
屏幕上内核日志滚到：

```
PCI configuration begin
IOPCIConfigurator::configure() PCI configuration PCI0
```

### 第一次尝试：加 `npci=0x2000`

Dortania 的经典条目，1401 的 `bootfix.py` 里有**逐字对应**的规则（连自测用例都用这行字符串）：

```python
# Dortania troubleshooting, "Stuck on [PCI configuration begin]": npci=0x2000, then npci=0x3000
if re.search(r"(?i)IOPCIConfigurator|PCI configuration (begin|PCI)", joined):
    out["args"].append("npci")
```

于是往 `NVRAM → Add` 的 `boot-args` 末尾加了 `npci=0x2000`。

> 注：1401 默认**故意不加** `npci`（`policy.py`：*"npci, IOPCIFamily patches and ProvideCurrentCpuInfo
> were never in it, so they are not added here either"*），它是靠 bootfix 阶梯在遇到该卡点时才补上。
> 且 installer 专用的 BAR 档位（`ResizeAppleGpuBars=0` + `ResizeGpuBars=-1`）我们的配置本来就有。

### ⚠️ 勘误（重要）：`npci=0x2000` **从来没有生效过**

最初我们把"越过 `PCI configuration begin`"归因于 `npci=0x2000`。**这个归因是错的。**
四份日志一起看，事实是：**在所有有日志的引导里，内核拿到 `boot-args` 里都没有 `npci=0x2000`。**

```
OCVAR: Setting NVRAM 7C436110-...:boot-args - ignored, exists     ← 配置里的值被忽略
AAPL: #[EB|MBA:NV]  <"-v debug=0x100 ... ipc_control_port_options=0 slide=246">
AAPL: #[EB|MBA:OUT] <"-v debug=0x100 ... ipc_control_port_options=0 slide=246">
                     ^^^^^^ 没有 npci=0x2000
```

规则是（`OpenCoreNvram.c`）：

```c
VOID OcLoadNvramSupport (...) {
  OcDeleteNvram (Config);   // 先删
  OcAddNvram    (Config);   // 后加
}
```

而 `OcAddNvram` **硬编码 `Overwrite = FALSE`**：

```c
      OcSetNvramVariable ( ..., NULL, FALSE /* Overwrite */ );
```

`LegacyNvramSupport.c` 据此：**变量已存在 → 直接打印 `ignored, exists`，不写。**
唯一能清掉它的是 `Delete` 阶段，而 `Delete` 里当时只列了 `ForceDisplayRotationInEFI` 和
`csr-active-config`，**没有 `boot-args`**。→ 变量被 boot #1 那次写入的值永久冻住。

**所以第一次"越过了"一定是别的原因**（很可能只是那次静默的 DMG 校验阶段被读成了卡死），
`npci` 这个变量**从未被真正检验过**。→ 见 [受控实验记录](05-受控实验记录.md) 第一轮。

### 一个会误导人的同款日志

`csr-active-config` 也在 `Delete` 里，却同样报 `ignored, exists`。这不是"Delete 不生效"。
`OcDeleteNvram` 在变量**同时出现在 `Delete` 和 `Add`** 时会比较二者内容：

```c
          if (SameContents) {
            DEBUG ((DEBUG_INFO, "OC: Not deleting NVRAM %g:%a, matches add\n", ...));
            continue;   // 内容相同就不删，保护 Flash 寿命
          }
```

`csr-active-config` 现存值恰好等于配置值 → **故意不重写**。这是设计行为。

### 为什么 `slide=246` 会混进 `MBA:NV` 却不在 NVRAM 里

`CustomSlide.c`：第 507 行用 `GetVariable("boot-args")` 读**真实存储值**，第 522–524 行把
`slide=%-03d` 追加上去，第 807–809 行接管 `gRT->GetVariable` 把这个副本回给 Apple 引导链，
第 585 行 `HideSlideFromOs()` 再从 XNU 命令行与 DT 里删掉：

> *"Having slide=X values visible in the operating system defeats the purpose of KASLR."*

→ OpenCore **只在读取时"贴"上 `slide=`，从不写回固件变量**。好处是 `Delete` 的内容比较用的是
干净的真实值，判定不会被 slide 干扰。

### 观测盲区：这一行之后**必然**看不到任何东西（源码补记，2026-10-19）

`IOPCIConfigurator::configure(uint32_t)` 的实际执行顺序（行号取本机
`audit/iopicifamily/` 副本；上游 `IOPCIFamily-681.140.3` 同名函数起点约在 `:3320`，
行号相差十几行但结构一致）：

| 本地行 | 语句 | 可见性 |
|---|---|---|
| `:3310` | `if (bootConfig) IOLog("[ PCI configuration begin ]\n")` | **可见** |
| `:3321` | `IOLog("[IOPCIConfigurator::%s()] PCI configuration %s\n", __func__, …)` | **可见** |
| `:3342` | `getPlatform()->setConsoleInfo(0, kPEDisableScreen)` | ← **从此行起屏幕关闭** |
| `:3346` | `doConfigure(options)` | 全部不可见 |
| `:3377` | `setConsoleInfo(NULL, kPEEnableScreen)` | 恢复屏幕 |
| `:3388` | `IOLog("[ PCI configuration end, bridges %d, devices %d ]")` | **可见** |

两条可见消息相隔 11 行，而**屏幕在第 3 行就被关掉**。
⇒ 「最后可见行 = 卡住的指令」不成立：遮挡区间覆盖整个 `doConfigure()`。
但**反向推论同样不成立** —— 见下面两条限度。

> **⚠️ 2026-10-19 复核：本节初稿里"所有等待都有 900 ms 上限 ⇒ 一定是真停住"的结论已撤销。**

**限度 1：屏幕可能再也回不来，即使 `configure()` 正常返回。**
恢复分支（`:3348-3382`）里若 `fConsoleRange` 有效而 `fConsoleRange->start == 0`，
则 `fPFMConsole = 0`，代码只走 `DLOG("!! lost console !!\n")`（`DLOG` 在 RELEASE 不输出），
**`kPEEnableScreen` 不会被调用**。⇒ 黑屏本身**不**证明 `doConfigure()` 没有返回。

**限度 2："900 ms 一定收得住"作废。**
- `kIOPCIEnumerationWaitTime`（`IOPCIPrivate.h:58`）只是 `waitForLinkUp` / CRS 这两类等待的初值，
  **不是 `doConfigure()` 的总时间预算**。
- 其起点 `fResetStartTime` 会被后续代码**重新刷新**（例如 `bridgeRetrainMask` 内 `:3057-3059`
  重写 `fResetStartTime` 并把 `fResetWaitTime` 改成 `kIOPCIWaitForLinkUpTime`），
  所以局部预算是可续期的。
- 链路训练、设备复位、`retrainLink` 各有独立条件；**单次 config 访问本身也可能永远不返回**（硬件层）。
- `iterate()` 里的 `if (++revisits > (8 * fBridgeCount))`（`:3258-3263`）只限制
  **同一次遍历中的回退重试次数**，**不是整个函数的超时保护**。

⇒ 「10 分钟没有新屏幕输出」只能登记为**可见进展停止**，
**不能**断言内核已死在某条指令上，也**不能**用"再等更久"或"不用等"来替代实验。

## 3. 内核跑得很远，然后停住 —— booter 内存映射 quirk（进行中）

### 现象
越过 PCI 枚举后内核推进得很深，最后几行（照片放大后读取）：

```
AppleACPICPU: ProcessorId=0..15 LocalApicId=... Enabled     ← 16 个逻辑核全部启用
ASP: Initializing bastion sandbox callback
no external trust caches found (segment length is zero)
IOAPIC: Version 0x21 Vectors 64:87
IOAPIC: Version 0x21 Vectors 88:111
ACPI: Executed 29 blocks of module-level executable AML code
ACPI: sleep states S4 S5
RTC: Only single RAM bank (128 bytes)                       ← 最后一行
```

> 勘误：低分辨率照片里的 `IOAPIC: Version 0x21 Vectors 64:87` 曾被误读成 `Assertion failed: (map->GetMMIOBase() != 0)`。
> **放大裁切后确认没有断言**。教训：看不清的行不要猜，放大再读。

### 1401 诊断器的判定
把 U 盘上 4 份日志喂给 `p1401.bootfix.findings()`：

```
startimage_aborted: False    stop16: False    no_slide: False
devirt_ran: True             mmio: 5 个区域
boots:                                      # findings() 只收入「跑到 EXITBS」的引导
  {stamp 2026-10-12T23:55:51, installer True, devmmio True, wrunprot False, macos_disk False}
  {stamp 2026-10-13T00:10:46, installer True, devmmio True, wrunprot False, macos_disk False}
  {stamp 2026-10-13T00:24:13, installer True, devmmio True, wrunprot True,  macos_disk False}
```

`handoff_stuck()` 的判据（`bootfix.py` 第 38–51 行）是：**用户说卡在 EXITBS，或
「安装器引导 ≥ 2 次、且始终没有 macOS 卷出现在内置盘上」**。本机条件满足 → 按阶梯改 quirk。

> **注意这条判据的措辞**：它推断的是"卡在交接之后（`first restart` 之前）"，
> 也就是隐含假设**内核从未打印**（第 156–158 行注释：*"the screen freezes on EXITBS:START,
> the kernel never prints"*）。**这个假设在本机不成立** —— 见下。

### ⚠️ 勘误：第 1 次引导根本没到 boot.efi

`logs/opencore-2026-10-12-233441.txt` 只有 43 KB，正文 459 行，**最后一行是**

```
37:517 00:011 OCB: Found chunklist BaseSystem.chunklist for DMG BaseSystem.dmg[10]
```

也就是**卡在 DMG 分块校验里**（就是第 1 节那个静默的长阶段），**`boot.efi` 从未启动**。
它没有 `AAPL:` 行，也没有 `MMIO devirt` 行。所以「4 份日志 = 4 次引导」是不对的：
**只有 2、3、4 这三次真正把控制权交给了 boot.efi。**

### ⚠️ 勘误：阶梯第一档是在**错误前提**下被套用的

阶梯第一档的触发逻辑认为"内核从未启动"。但屏幕照片证明**内核已经跑起来了**：

```
AppleACPICPU: ProcessorId=0..15 ... Enabled     ← 16 个逻辑核全部启用
IOAPIC: Version 0x21 Vectors 64:87
IOAPIC: Version 0x21 Vectors 88:111
ACPI: Executed 29 blocks of module-level executable AML code
ACPI: sleep states S4 S5
RTC: Only single RAM bank (128 bytes)           ← 最后一行
```

配合日志里 `EXITBS:START` 之前完整记录了 kext 注入、27 条内核补丁、
`Only 175/256 slide values are usable` 等 —— **"交接后就再没有任何输出"是假的**。
屏幕上这些行全是 ExitBootServices **之后**的内核输出。

> 另一个容易踩的坑：日志文件里的 `AAPL:` 行是 boot.efi 的输出，被 OpenCore 并进了同一个日志；
> **内核自己的输出不会落盘**（交接后 OpenCore 不再写文件）。所以"日志停在 EXITBS" +
> "屏幕还在滚"是在同一时刻并存的，两者不矛盾。

结论：**不能用"日志止于 EXITBS + 没有 macOS 卷"推断"死在交接"。
第一档改动的那个前提（放弃 MAT 组合）对这台机器不成立。** 详见
[受控实验记录](05-受控实验记录.md) 的 D3。

### 顺带更正一处前提：`handoff_stuck()` **并没有被删掉**

有说法称"最新 1401 源码已经没有文档所说的 `handoff_stuck()` 规则"。**核对后不成立：**
`1401\extracted\1401\engine\app\p1401\bootfix.py`（1.14.2）**第 38 行**定义了
`def handoff_stuck(f, stopped_at="")`，**第 165 行**以 `stuck = handoff_stuck(f, stopped_at)`
实际调用它。而且它确实执行了 —— 第 4 次引导的 `OCABC:` 运行时值与第 167–176 行的 `nomat`
集合逐位吻合，卡上那份 `DevirtualiseMmio=False` 也与第 177–182 行 `bootlog-handoff-devirt`
的输出吻合。**问题不是"规则不存在"，而是这条规则在本机的前提为假。**

### 阶梯第一档 `bootlog-amd-exitbs`

```
Booter.Quirks  DevirtualiseMmio        True   → True
               SetupVirtualMap         True   → True
               RebuildAppleMemoryMap   True   → False
               EnableWriteUnprotector  False  → True
               SyncRuntimePermissions  True   → False
```

源码里的实测记录：*"measured on a Ryzen 5 5500 / B550 (10-09)：默认配置下挂死，换成 MMIO 那组过去了，
再打开 write-unprotector 那组才不 panic。**五项必须一起改**。"*
**结果：第 4 次引导（`wrunprot 1`）仍然停住。**

> 但要注意这一档**把配置从 Dortania 的 MAT 组合切到了"无 MAT"组合**，而本机
> `OCABC: MAT support is 1`（固件**有** Memory Attributes Table）。Dortania `AMD/zen.md`
> 给"无 MAT"组合的**唯一前提**就是固件缺 MAT：
> *"…you may find that the above combo will result in early boot failures. This is due to
> **missing the `MEMORY_ATTRIBUTE_TABLE`**…"* → **前提不成立。**
> 同时必须说明：第 2、3 次引导**已经在跑 MAT 组合**，也一样停住 —— 所以两个组合**都**没能过关，
> 而那两次同样**都没有 `npci` 生效**，变量从来没被隔离干净。

### 阶梯第二档 `bootlog-handoff-devirt`（已撤下，未验证）

保留上组、把 **`DevirtualiseMmio` 翻成 `False`**，`ocvalidate` 复核 0 issues。
**这一档从未引导过**（最新日志 `DEVMMIO 1`，配置是 `False`），
因此在 [第一轮实验](05-受控实验记录.md) 中已被**主动撤回**，避免把"未测试"当成"已失败"。

**这跟 §3 记的"最后一行 = `RTC: Only single RAM bank (128 bytes)`"不是同一个停点。**
`RTC:` 属极早期（`AppleRTC`），而 `AppleKeyStore` / `AppleSSE` / `CoreAnalyticsHub`
都是内核启动**末段**才运行的 kext。⇒ Rounds 6/7 已经越过 `RTC:`，跑得比本文件记录的更远。
**"停在 PCI 枚举"这个沿用七轮的说法需要改写。**

**⚠️ 2026-10-19 复核（用户审核）：初稿"首次配置 / 第二次配置"的二分法**已撤销**。**
`[ PCI configuration begin ]` 在源码里有**两个出处、两种宏**，屏幕本身分不出是哪一个：

| 出处 | 宏 | 门控 | 伴随后续 |
|---|---|---|---|
| `configure(uint32_t)` `:3310` | `IOLog` | **`bootConfig` 为真** | 紧跟 `:3321` 的 `[IOPCIConfigurator::%s()] PCI configuration %s` |
| `configOp()` 的 `kConfigOpScan`/`kConfigOpRealloc` `:446` | `DLOG_A`（调试宏） | 取决于该 RELEASE 内核里 `DLOG_A` 是否编译生效 | 对应 end 在 `:449`，带独有尾巴 `changed %d, waiting %d` |

再叠加两条事实：
- `:3321` 那条 `IOLog` **没有** `bootConfig` 门控 ⇒ 任何 `configure()` 调用者都会打印它；
- `configure()` 的调用者有两类：`addHostBridge()` → `configure(kIOPCIConfiguratorBoot)`（`:706`，
  本机树中唯一带 boot 标志的调用点）与 `configOp()` → `configure(0)`。

**可以确定的只有一点**：屏幕上那两行紧挨着，而源码里它们只隔 11 行
⇒ 来自**同一次** `configure()` 调用。该次调用打印了 "begin"，因此只有两种可能：
① `bootConfig == true`（调用者是 `addHostBridge()` 的 boot 配置）；
② 或 `DLOG_A` 在该内核里实际生效（调用者可能是 `configOp()` 的重配置）。

**不能确定的**：`DLOG_A` 是否生效 —— 判断它需要内核侧输出，目前没有这个通道。
（一个**弱**反面线索：`configOp` 版本的 end 消息带 `changed %d, waiting %d`，七轮里从未出现过；
但"卡住看不到"同样能解释，所以它不足以定论。）

⇒ **不得把这一对消息直接判为"IOMMU / AppleVTD 晚期重配置"。**
Round 10 只建立观察基线，**不承诺**分辨首次/二次配置；若录像里出现更早的同一组日志，
也只能作为**证据等级较高但仍需交叉核对**的观察，不能自动归因于 AppleVTD。
